# Hadith Bank reader data-host migration

**Status: design approved; not implemented.** This is a handoff for an isolated, local pilot, not a deployment authorization. Start from the recorded [source baseline `1a865c6c3585815ea4132b96b69240f5ed3a6635`](https://github.com/blaghtayt-alt/Hadith-Bank/commit/1a865c6c3585815ea4132b96b69240f5ed3a6635); re-read current `main`, the live reader and in-flight changes before using it. Record source, generated artifact and live release identities separately.

## Contract: what moves and what stays

- Keep **one [public reader](https://blaghtayt-alt.github.io/Hadith-Bank/), one search, and the existing occurrence, book, edition and language URLs**. The data host serves generated assets, not a second public reader. Preserve exact occurrence IDs, collection/edition and language filters, deep links and citation behavior.
- Move only approved, reproducible **generated reader data** for the pilot. GitHub remains the source of truth for material registration, exact source editions, associated source PDFs/OCR and provenance. Preserve source access, original links and limitations. Keep static HTML/no-JavaScript reading and discovery, canonicals and the sitemap on the existing site. Do not trade these for a JavaScript-only shell, change stored source text, or silently move/delete originals.
- Keep one exact occurrence and its reviewed language-version links. Reuse Arabic/English text through existing verified identifiers only, preserving exact variants, per-edition citations and attribution, missing/link-only distinctions, and unreviewed/held statuses. No duplicate records, heuristic rematching, translations, or canonical merges as a transport side effect. Never demote a verified exact version or turn an unresolved link into a text counterpart.
- No source acquisition in this pilot. For later acquisitions require explicit source scope, authorized access/use, an identifiable edition and translator/provenance, exact retained evidence, duplicate/disposition checks, and separate review/release authority. If evidence or access is insufficient, stop and report; do not fill gaps, substitute an unapproved source or bypass restrictions.

## Pilot design

1. **Reconcile ownership.** Inspect current main, changed paths and owners before starting; coordinate with [PR #20](https://github.com/blaghtayt-alt/Hadith-Bank/pull/20) first because the reader code overlaps. Preserve [#7](https://github.com/blaghtayt-alt/Hadith-Bank/pull/7), [#22](https://github.com/blaghtayt-alt/Hadith-Bank/pull/22), blocked [#23](https://github.com/blaghtayt-alt/Hadith-Bank/pull/23), [#25](https://github.com/blaghtayt-alt/Hadith-Bank/pull/25), [#30](https://github.com/blaghtayt-alt/Hadith-Bank/pull/30) and the workflow safeguards in [#31](https://github.com/blaghtayt-alt/Hadith-Bank/pull/31)/[#32](https://github.com/blaghtayt-alt/Hadith-Bank/pull/32). These are coordination references, not claims about current PR state. Do not change, supersede, rebase or trigger someone else's work. Stop on concrete overlap.
2. **Use one already-published language**: Japanese (`ja`), subject to current live evidence and no owner overlap. Record exact selected occurrence IDs and all generated shard dependencies and confirm every non-pilot language stays unchanged. If the published slice cannot be accurately isolated (including mixed-language shards and shared indexes), report why and ask before changing scope. Do not move a mixed shard containing unrelated payload merely to shrink a headline number.
3. **Use a versioned immutable release.** Bind one trusted reader configuration to an explicit deployment data root, exact source revision, one versioned manifest and its SHA-256. Include each asset's relative path, expected byte length and SHA-256, schema/version, and the byte representation checked (including compression). Validate before use, including on warmed caches. The existing loader is constrained to the same-origin sibling `hadith-bank-reader-data/` and rejects invalid/disallowed directories. A new data root needs an explicitly validated transport change, not a URL substitution, fallback origin, user-controlled query/path or relaxed directory checks. Constrain the scheme/origin/root, requested paths and redirect behavior; reject mismatches without indexing or rendering unverified data.
4. **Prefer a same-origin delivery design where supported.** If a separately authorized cross-origin deployment is required, restrict requests to the approved HTTPS origin and exact release root, configure CORS for the actual reader origin, omit credentials, and fail closed on denied, opaque, misdirected or invalid responses. Never use a general proxy, permissive fetch fallback or disable verification. Confirm site and data workspace/build behavior before proposing either host arrangement.
5. **Plan two distinct deployments.** Only after approval, publish versioned data first; independently verify real endpoint manifest/assets from the exact reader origin. Then deploy the reader pointing to that verified release and verify actual live identity. Cache immutable versioned assets; revalidate the release selector/HTML; never reuse a digest for different bytes or mix versions. Document rollback to the last verified reader/data pair, keep rollback data available, and exercise cold, warm, stale and offline cases. If data fails, preserve static browsing and show an explicit availability error; never silently search an incomplete corpus as if it were complete. Do not ship both local and remote copies of the moved assets in the active pilot payload.

## Acceptance evidence before any rollout

- Build a **fresh full-corpus baseline and staged full-corpus candidate** at recorded, comparable revisions. Measure final deploy tree bytes, generated data bytes, path-level deltas, external asset bytes, combined footprint and largest objects. Distinguish compressed transfer, unpacked and on-disk bytes. Audit duplicates across hosts and verify the actual replacement rather than extrapolating from a sample. Keep the **950,000,000-byte production guard** and aim for **at most 900,000,000 bytes** on Pages, unless the owner separately changes the target. About **929.5 MB site** and **304 MB reader shards** are historical report figures, not current live sizes, guarantees or a subtraction formula.
- Require exact source-byte preservation and before/after counts and occurrence IDs across every language plus each Japanese dataset. Compare actual Arabic/English counterpart text, IDs, qualifications and link-only/missing states. Verify correct decompression, manifest and shard integrity, missing/corrupt file rejection, mixed-version rejection, and no extra or unreachable deployed assets for the moved slice.
- Run cold and warm search measurements on the same dataset and representative devices/network: request counts and bytes, time to first results, full text in Japanese/Arabic/English, filters, occurrence detail and counterpart opening, and representative deep links/book routes. Check static pages with JavaScript disabled, sitemap/canonical continuity and no-JavaScript usability independently. Test offline behavior, host/CORS failure and real rollback on staged infrastructure; record any change to existing offline behavior explicitly.
- Return one resumable receipt: verified source/current head, path/owner conflict check, exact pilot manifest/revision and digests, baseline vs staged measurements, preservation and browser/test evidence, actual blockers, rollback instructions, and what is still local versus live. Do not claim migration success from a design, local build, PR-only validation, or a successful workflow with publication skipped.

**Approval boundary:** prepare, inspect and test locally only. Do not push, open/change PRs, provision or configure a host, pay for anything, alter/dispatch workflows, deploy, or change audience/access before separate explicit approval. Stop if a required input, owner or release binding is unresolved.
